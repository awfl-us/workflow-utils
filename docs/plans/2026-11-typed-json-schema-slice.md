# Phase 1.1 — in-memory typed JSON Schema

**Status 2026-11-19:** implementation and standalone test verified on branch `feat/reconcile-typed-json-schema` from `main` (`a7116e5`). No production behavior, schema-file generation, runtime routing, publishing or deployment changes.

## Historical review and selection

Historical `wip-old` (`e73cafd`) supplied an `Ista`/`Kala`-coupled `JsonSchema` implementation, a hand-written JSON renderer, `Llm.ToolDefProperty` converter and an unsupported-type fallback using runtime `sys.error`. Those concerns do not need to enter the first integration slice. The new `utils.JsonSchema` derives **in-memory** schema representations using Scala 3 `Mirror` and `compiletime`, supports primitives, case classes, sealed sums, collections/maps, `Option` and AWFL DSL `Value`/`BaseValue`/`ListValue`/`OptBase`/`OptList`. Unsupported types fail **at compile time**. No new dependencies or compiler-generated files.

The returned `Map[String, Any]` is intentionally an intermediate representation, not yet a serialized OpenAI tool or validated decoder. JSON-schema nodes include object `additionalProperties=false` for case classes. Optional fields are absent from `required` and accept null; optional DSL list fields use `oneOf[array,null]`. Maps retain typed `additionalProperties`.

## Verified tests

`/opt/sbt/bin/sbt -batch 'Test/runMain us.awfl.utils.JsonSchemaSpec'` **PASS** with Scala 3.3.1 / current DSL 0.3.5: primitive fields, `Value`, `ListValue`, optional wrappers, nested collections/maps, sealed `Result`, document metadata and compile-time rejection of `java.time.Instant`. No ScalaTest dependency; standalone test entrypoint fits current repo.

## Next slice / acceptance gates

1. Add contextual `Ista[T]` descriptions without making schema derivation require a `KalaVibhaga`. Avoid mixing metadata/routing fields into model-visible JSON.
2. Implement a typed `Llm.ToolDefProperty` conversion with the actual current server contract. Consider rendering JSON only at the appropriate API boundary.
3. Implement argument decoding / validation separately (e.g. reject missing and malformed typed results).
4. Publish a deliberately versioned library only after workflow integration tests and native Rust Project Manager fixtures remain green. No release or merging for this slice alone.

## Phase 1.2 verified — contextual metadata and model-facing tool adapter

On `feat/reconcile-typed-json-schema` (not merged/published), extended the existing `Ista[T]` value with an optional backward-compatible `description: KalaVibhaga => String` parameter. Existing two-argument `Ista(name, build)` callers compile without changes; new typed functions may supply a context-specific description (tested SegKala vs SessionKala). `JsonSchema.functionForIsta[T]` derives `ModelFunction` with exactly `type=function`, `function.name`, `function.description` and lossless `function.parameters`. `RoutedTool` holds the internal workflow name **outside** the model-facing JSON. No routes, model calls or agent workflow behavior were changed.

**Compatibility constraint:** current `Llm.ToolDefProperty` cannot express `oneOf`, nullability, typed `additionalProperties`, or `additionalProperties=false` on normal case-class objects. Historical `wip-old` silently downgraded these. `JsonSchema.legacyProperty` now explicitly throws for unsupported objects/unions/maps; it is usable only for faithfully representable primitive and primitive-array nodes. `JsonSchema.function[T]` is the canonical model-facing path. It preserves nullability and strict object/map constraints in memory, but has **not** yet been sent through the current Jobs LLM API, which may need a schema serialization/strict-mode contract update.

**Tests:** `sbt -batch 'Test/runMain us.awfl.utils.JsonSchemaSpec'` passed under Scala 3.3.1, including contextual Ista text, required/optional/union constraints, absence of routing metadata from model JSON, rejection of non-object tool inputs, and fail-closed legacy conversion. Unchanged current Project Manager baseline revalidated: 26 native Rust ELF workflows, 15/15 real PostgreSQL tests, 22 durable journal passes (1 optional skip), 3/3 strict background agent scenarios; **no new schema is wired into that baseline yet**.

Next: align server OpenAI request DTO to transport full tool schema; add deterministic JSON rendering and typed arguments decoder/validator with missing/extra/nullable fields; then test an actual tool/schema round-trip through native compiled workflow and real Jobs + provider contract. Do not merge the old `wip-old` Sadhaka or compiler schema writer.

## Phase 1.3 — canonical serialization and typed model response validation (2026-11-19)

**Current status: code implemented on separate review branches, all tests green; not merged/deployed.** `JsonSchemaCodec` serializes all model-facing nodes deterministically, sorting object keys recursively and escaping control characters, without introducing a JSON library dependency. `JsonSchema.nativeTool[T]` and `nativeToolForIsta[T]` embed the exact schema in the existing Scala `Llm.ToolFunctionDef` through a `json.decode` CEL expression rather than weakening it to historical `ToolDefProperty`. This compiles under Scala 3.3.1 with current DSL 0.3.5, preserves nullable unions/strict object constraints, and retains the same `tools` HTTP field. The expression's **runtime evaluation inside a newly compiled native Rust agent remains a specific next gate**.

On the server `fix/reconcile-background-fixtures` branch, new `jobs/llm/typedToolArguments.js` validates incoming returned tool-call JSON against the full schema, preserving required/optional/null/map/list/integer checks; unknown function names and unsupported schema keywords fail closed. The existing Jobs `/llm/chat` route has an **opt-in** `validate_tool_arguments=true` flag; default callers are unchanged. Failed typed responses return 422 with sanitized field-path errors after normal model usage accounting (model inference still incurred cost). `jobs/providers/openai.js` already passes structured `tools` unchanged; no new HTTP schema field or provider rewrite required. The legacy `Llm.ToolDefProperty` converter remains deliberately fail-closed.

**Cross-repo contract verification:** Run `AWFL_TYPED_SCHEMA_FIXTURE_PATH=/tmp/awfl-reconcile-typed-schema.json sbt -batch 'Test/runMain us.awfl.utils.JsonSchemaSpec'` in workflow-utils, then `AWFL_TYPED_SCHEMA_FIXTURE_PATH=/tmp/awfl-reconcile-typed-schema.json node --test jobs/llm/typedToolArguments.test.js jobs/llm/typedToolSchemaContract.test.js jobs/providers/openai.test.js` in server. This uses the actual canonical Scala-generated JSON and verifies provider request preservation plus valid/invalid response decoding; **9/9 Node tests** passed. No real OpenAI request was made.

**Follow-ups:** (1) Compile a new native Rust workflow that uses `JsonSchema.nativeTool` and verify actual decoded JSON in an HTTP effect; (2) exercise `validate_tool_arguments=true` through the full authenticated Jobs app including 422/cost event; (3) validate typed outputs through the existing tool dispatcher and native recovery; (4) consider whether malformed tool calls should be returned as a normal structured tool error instead of endpoint 422. Until then, keep draft PRs and do not claim end-to-end typed tool execution.

## Phase 1.4 — ergonomic `Ista.tool(kala)` native path verified (2026-11-19)

**Decision:** retain the historical use-site ergonomics, not the historical lossy `JsonSchema.toToolDef` converter. Call sites use `ista.tool(kala)`. Schema derivation remains type-checked at compile time by `JsonSchema.derive[T]`, which produces a typed `Schema` algebra; the final boundary lowers its `toJsonValue` to an `Obj[Map[String, Any]]` inside the existing `Llm.ToolFunctionDef`, with **no JSON string and no `json.decode`**. Existing `ToolDefProperty` call sites remain unchanged; `ToolFunctionDef.parameters` widens to `BaseValue[?]` because the DSL `SpecBuilder` cannot derive a union-typed field (`BaseValue[ToolDefProperty] | BaseValue[Map[String,Any]]` was tried and rejected by the Scala compiler). This intentionally confines the less-specific type to the already-heterogeneous JSON wire boundary rather than weakening `JsonSchema.Schema`. No changes to `dsl`, `compiler-rust` or generated-schema files.

**Verified native execution:** Built `helpers-TypedIstaSchemaFixture` via existing Scala→Rust compiler, compiled a static musl ELF, executed it with `NativeMemoryExecutionPilotStore` and isolated PostgreSQL and asserted the resulting JSON. Required/optional fields, `oneOf`, explicit null, strict `additionalProperties=false`, a map with typed integer values, nested array item types and Kala-sensitive descriptions survived **exactly**. `jobs/providers/openai.buildChatPayload` preserved the native tool; `parseTypedToolCalls` accepted a valid payload and rejected incorrect map-value types. Completed native workflow replay returns the identical result. No actual model call. Full current Project Manager regression closure: **26 ELF workflows, 3/3 strict background scenarios, 15/15 PostgreSQL integration, 22 durable-journal passes with 1 optional skip**, and Scala schema unit suite.

**Repeat:** In workflows run `PGTEST_URL=postgres://awfl@127.0.0.1:55439/awfl_reconcile ./scripts/reconcile-test typed-ista --server ../server --compiler ../compiler-rust` with a local `0.3.6-SNAPSHOT` of this branch published by `sbt 'set ThisBuild / version := "0.3.6-SNAPSHOT"' publishLocal`.
